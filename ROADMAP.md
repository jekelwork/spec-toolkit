# Roadmap

Plan-only ledger for the spec-driven development toolkit. GitHub issues and pull requests hold
progress; see [docs/roadmap-format.md](docs/roadmap-format.md) for the format.

## Planned Specs

### 001 — Guided bootstrap [status: planned]

- **Description:** A conversational, resumable bootstrap: a `bootstrap.py start` engine with
  machine-readable status, and a `bootstrap-guide` skill that walks the user through it in their
  coding agent.
- **Outcome:** After "Use this template", an adopter reaches a merged bootstrap pull request and a
  first roadmap sync by talking to their coding agent, can ask questions along the way, and can
  stop and resume at any step.
- **Scope (in):** Phase 1 engine: resumable steps for the bootstrap issue and branch, `init` with
  board creation, `github` preview and `--apply`, the board token check, the pull request, and the
  first roadmap sync (preview, then apply after confirmation); `check --json` status; terminal
  prompts only as a fallback. Phase 2 skill: reads state from the engine and explanations from
  `docs/bootstrap.md`; "guide me" or "do it for me" mode; decisions (description, visibility,
  approvals, constitution, roadmap) always by the user; changes that bypass pull request review
  only after a preview and an explicit yes; the board token set by the user in the terminal or
  the GitHub web page, never pasted in chat (a pasted token stops the flow: revoke, create a new
  one, set it again; the agent never uses it), confirmed with `gh secret list`; guidance for the
  classic token's scopes and the board's "Pull request linked to issue" workflow.
- **Scope (out):** a full interactive terminal wizard; a general process-help agent; platforms
  other than GitHub.
- **Depends on:** none
- **Notes:** It is a skill, not a sub-agent, because sub-agents cannot hold a conversation with the
  user. The skill reads the process from the engine and the docs and keeps no copy of its own.
  Open questions for clarify: the `check --json` fields and how the format is versioned; how the
  skill is tested (a test that every command and doc section it names exists, plus a manual
  walkthrough on a pilot repository after each Phase); where the chosen mode is kept when
  bootstrap resumes in a new session (stored by the engine, or asked again). Process help after
  bootstrap is a "where to find what" index in `AGENTS.md`, done as a separate chore. Users who
  do not code themselves are not a target yet; the design keeps that option open.

### 002 — GitLab support [status: undecided]

- **Description:** Let teams on GitLab adopt the toolkit with the same process as on GitHub.
- **Outcome:** A GitLab project can create, plan, track and gate work with the toolkit.
- **Scope (in):** separate the GitHub-specific parts of the scripts; GitLab CI equivalents of the
  workflows; `glab` and the GitLab API; issue boards and epics for the roadmap and Phase tracking;
  merge request approval rules and protected branches; the agent file output.
- **Depends on:** none
- **Notes:** Whether and when is undecided. Some needed GitLab features may require paid tiers;
  check before specifying. GitLab users can already copy the template with plain Git.

### 003 — Blast radius report [status: planned]

- **Description:** A short blast radius report for every piece of work: which agent profile should
  handle it, whether one of the project's irreversible failures is in reach, and which other work in
  flight cites the same files. It is written in `plan.md` for a roadmap feature and in the issue
  body for a typed issue, and a script rechecks the collisions when a branch starts.
- **Outcome:** Before a branch starts, the team sees whether the work collides with other open
  issues or Phases and whether it comes near an outcome nobody can undo. Work near such an outcome
  is reviewed by an agent on the `critical-review` profile, such as `code-reviewer`, before it
  starts.
- **Scope (in):** An irreversible-failure list and a route-to-profile table (profiles from
  `agents.toml`) in `project-context.toml`, set per adopter. A collision script that reads file
  citations from the bodies of open typed issues and from the `tasks.md` and `plan.md` of features
  with open Phases, accepts a draft, and reports how much it compared. A Blast radius block written
  when a typed issue is created, listing the files it expects to change, the route and profile, any
  irreversible failure in reach, and its overlaps with the counts compared, with the `AGENTS.md`
  rule for it. The collision recheck in `roadmap-dependency.check` (`before_implement`, as a
  warning, never part of the blocker set) and when a typed-issue branch starts. A Blast radius
  section in `plan.md`, added by a hook because the plan template and the `speckit-plan` skill are
  generated by Spec Kit. A hidden provenance line at the end of each report, giving the route, the
  profile and how much was compared.
- **Scope (out):** Blocking a branch or merge on a collision (it is a warning); a report per `T###`
  task; line-level collisions for `tasks.md`; platforms other than GitHub.
- **Depends on:** none
- **Notes:** Adapted from the Factory Kit's `triage-work-items` skill and its `collisions` report.
  How the kit does it, for reference only (clarify decides whether to adopt its first-stage
  classifier): a first-stage agent on a cheaper model classifies each item against a route table the
  project owns, ignores the item's own category, and returns JSON with the route, whether an
  irreversible failure is in reach and which one, the likely files, the recommended model and a
  one-sentence reason; when unsure it escalates. The analysis then runs on that model. A route whose
  worst outcome is an edit somebody notices goes to the cheaper model, and one whose worst outcome
  is a confidently wrong answer nobody can check goes to the stronger one. A row can escalate on its
  own condition, for example an API route when the response shape is public, or a capability when a
  shared contract changes. The irreversible-failure list holds two or three concrete outcomes that
  nobody can undo and nobody notices by looking. When one is in reach, the Blast radius section
  names it in its first sentence, with direction and magnitude; otherwise it says in one sentence
  that nothing is in reach. The collision report reads only the last posted plan on each open item
  (a revision supersedes the plan before it) and extracts `path:line` and `path:from-to` citations.
  Bare filenames count, resolved against `git ls-files` only when the basename is unambiguous,
  because a guess invents collisions. It groups citations by file and classifies each pair of items:
  same lines when the ranges intersect (do not branch both), same area within 60 lines (sequence
  them), and same file when there are no line numbers or a range is wider than 40 lines (parallel
  work is possible, with mechanical conflicts). It keeps the tightest evidence per pair, never the
  union of spans, and withholds a confidential item's files and lines while keeping the overlap. The
  kit's version has four blind spots, and this design closes them. The item being analysed is not
  compared, because its plan is not posted yet (fix: a draft option). "No overlap" and "nothing
  compared" print the same message (fix: report the counts). A plan under a hand-typed heading other
  than the marker is silently ignored (fix: code writes the heading, as `ensure_issue_comment` in
  `scripts/github_issue_comments.py` already does with its marker). Files with an unlisted extension
  or none, such as `json` files and `LICENSE`, are invisible (fix: the file types adopters set in
  `project-context.toml`, or every file `git ls-files` lists, plus extensionless files by name).
  Citation overlap is still only a proxy for edit overlap. Why these places: `plan.md`, because the
  spec-and-plan pull request is the last point where the answer can still change the design; the
  issue body at creation, because the agent that files a typed issue already knows the files and the
  cause, and typed issues are worked in parallel with nothing ordering them; a recheck at branch
  start, because collisions depend on what is in flight at that moment. Not in a roadmap entry,
  because no files are known yet, and not per `T###` task, because that is too late and too fine.
  `tasks.md` paths carry no line numbers, so overlaps with Phases are reported per file. Each report
  ends with a hidden provenance line giving the route, the profile and how much was compared, so a
  reviewer can check the model and the comparison later. The kit's operational rules, for reference
  (adopted only if clarify adds them to Scope): write a report to disk before posting it, and keep
  four to six agents in flight with at most two on the strongest profile. Tune the 60-line and
  40-line thresholds to the code, since a missed collision is worse than a noisy one. Suggested
  order of work: the list and the route table, the collision script with its tests, the issue-body
  block, the branch-start rechecks, then the `plan.md` section. Typed issue #87 holds the first
  design. Open questions for clarify: which outcomes go on this repository's own
  irreversible-failure list (candidates: what `bootstrap_github.py` changes in a real repository,
  and what `export_toolkit.py` publishes); what triggers the recheck when a typed-issue branch
  starts (an agent rule, a lefthook hook, or a script that creates the branch); and whether the
  `plan.md` section comes from an `after_plan` hook (`speckit-plan` reads one, and none is
  registered yet) or from a separate step.

### 004 — Bootstrap-guide skill evaluation and simplification [status: planned]

- **Description:** Make the `bootstrap-guide` skill measurable, shorter and more deterministic: an
  evaluation that replays bootstrap situations through a real coding agent, the steps the engine
  can do itself moved out of the skill into `bootstrap.py`, and the remaining text split into a
  short core with linked reference files.
- **Outcome:** A change to the skill or the engine is checked by a repeatable evaluation instead of
  only by a manual pilot walkthrough; the skill holds only the conversation loop and the rules that
  need judgement, and is shorter than at the Phase 1 baseline.
- **Scope (in):** Phase 1 evaluation: scripted bootstrap scenarios (for example an exit-3 preview,
  a pending decision in `check --json`, the constitution step) replayed through an agent, and the
  transcript scored against the skill's rules (the preview in the agent's own message, the exit
  suffix only on commands the agent runs, no predicted next step, no yes taken from command
  output); a baseline recorded with the skill as it is when Phase 1 starts. Phase 2 deterministic
  steps into the engine: `bootstrap.py` prints what the agent now assembles by hand (the filled-in skill calls, an exit
  status line, the preview block, the closed list of commands), with the `check --json` and
  `start` contracts updated. Phase 3 split: `SKILL.md` keeps the loop and the hard rules, details
  move into linked reference files next to it that hold only the skill's own rules and still link to
  `docs/bootstrap.md` for explanations, and the guard tests follow the text.
- **Scope (out):** new bootstrap steps or decisions; changing who decides what; platforms other
  than GitHub.
- **Depends on:** 001
- **Notes:** Raised in #86 after pilot p5. Phase order matters: the evaluation baseline comes first
  so Phases 2 and 3 can show they make nothing worse, and the split comes last so it works on the
  text left after Phase 2. Open questions for clarify: the evaluation tooling (skill-creator evals,
  `claude plugin eval`, or our own harness); which coding agents the evaluation covers (Claude
  Code, Codex, Copilot) and how it handles nondeterministic answers (several runs, a pass rate);
  whether it runs in CI or on demand, given its cost; how much of the manual pilot walkthrough it
  replaces.

### 005 — GitHub App as the preferred board credential [status: planned]

- **Description:** Let every adopter, solo developers included, use a GitHub App as the preferred
  credential for the toolkit's board automation, and keep the classic personal access token as a
  supported, documented fallback. Clarify chooses between two designs: an organization-owned GitHub
  Projects board (the App needs an organization, a free one is enough), or an issue-based board that
  an App can serve on a personal account too.
- **Outcome:** An adopter understands the security trade-off between the App and the classic token
  (on the organization design, also what creating and owning a free organization involves) and,
  on the chosen design's App path, creates and installs a minimal App and sets its secrets
  without choosing permissions by hand and without the private key ever passing through the agent.
  An adopter who stays on the classic token still gets clear guidance.
- **Scope (in):** Both designs are compared in clarify; the work of the chosen one is built.
  Organization-board design: an owner decision (organization or personal account) early in the
  bootstrap engine and the `bootstrap-guide` skill, before the repository and board are set up,
  with the reason (GitHub Apps and fine-grained tokens cannot reach a Project owned by a personal
  account), and at that decision point, where the user chooses between the App and the classic
  token, an explanation that a private person can create a free organization in a few minutes
  without a company or any legal registration, how to create one, and what having it means for
  them: the organization owns the repository and board while they stay its owner; an existing
  repository can be moved there, and local clones keep working through GitHub's redirect but should
  update their remote with `git remote set-url`; a Projects board owned by the personal account
  does not move with the repository and has to be recreated under the organization; and the GitHub
  Free limits that apply. The App's minimal permissions on this design are repository Issues: read
  and organization Projects: write.
  Issue-board design: the board kept on the repository's issues instead of GitHub Projects, or the
  Projects board made optional, so the App needs only repository permissions; the changes this
  needs in the three board sync workflows, Phase tracking and the board creation of 001. For
  either design: App setup from a pre-filled App registration link or a GitHub App manifest, with
  the private key generated or downloaded by the user, never handled by the agent, and the secrets
  set by the user in their own terminal, as today; `check` and `github` report which credential is
  in use and recommend the App when a personal token is set where the App can be used (an
  organization board, or the issue-board design); `docs/bootstrap.md` Board credentials
  reordered with the App path first, the classic token as the fallback, and the security
  comparison; tests for the new steps and the guide's credential guidance.
- **Scope (out):** App user-to-server tokens (`ghu_`) for personal-account boards; moving an
  existing repository or board into an organization for the user; hosting a shared public App;
  platforms other than GitHub.
- **Depends on:** 001
- **Notes:** Discussed after a pilot test confirmed the limit: an App installed on a
  personal-account repository got "Could not resolve to a ProjectV2" for that account's board. The
  board owner must stay equal to the repository owner, so on the organization design the owner
  decision has to come before the repository or board is set up. The issue-board design comes from
  the Factory Kit, another agentic coding project template piloted in a separate repository: its
  board is the repository's issues, so its App works on a personal account. Clarify decides between
  the designs by comparing their steps and whether the process becomes simpler and easier to
  understand or gains steps. Security is the deciding factor: more steps or complexity are
  acceptable when they improve the user's security, and the chosen design must not expose the user
  to a security vulnerability through the template. 005's spec supersedes the classic token
  guidance of 001's FR-021; 001's text stays as history. On GitHub Free, organization secrets may
  not reach private repositories, so the App secrets may have to be set per repository, and a free
  organization does not unlock rulesets or required reviews for private repositories. Entry 004
  changes the same skill and engine; coordinate the order of their Phases, and if 005 lands first,
  004's evaluation covers the new steps. The wording fix for the classic `repo` scope is the
  separate chore #91. Open questions for clarify: whether the issue-board design needs an App at
  all, since the workflows already write issues with their own `GITHUB_TOKEN` (a third option, no
  extra credential, with the limit that `GITHUB_TOKEN` events do not trigger other workflows); the
  pre-filled link or the manifest (the manifest conversion returns the private key in an API
  response, so it must not run in the agent's shell); whether one App per organization is reused
  across repositories; how `start` handles an adopter who already created the repository under a
  personal account (keep the classic token, or explain the transfer).

### 006 — Bot identity for agent-made GitHub changes [status: planned]

- **Description:** Make the GitHub changes a coding agent makes from the user's machine (issue and
  pull request comments, issues, pull requests, labels, assignments and board updates) appear as
  the toolkit's GitHub App bot instead of the user, so the record shows what the AI wrote and what
  the person wrote.
- **Outcome:** On GitHub, the agent writes chosen in clarify are authored by `<app>[bot]`; every
  other agent write keeps its current author and is listed in the docs, and everything the person
  writes is authored by them. A decision the person makes in the agent session and the bot posts
  names the person who made it. The private key is never written to the repository or shown in the
  agent session, each use of it is gated by a step the agent cannot pass (chosen in clarify), and
  the agent's GitHub access is narrower than the person's own `gh` login it uses today. The bot
  cannot merge a pull request, no approval from it counts toward the required approvals, and the
  non-author approval rule keeps its meaning.
- **Scope (in):** A local way for agent-run scripts to get short-lived App installation tokens
  with the narrowest permissions for each task, kept in memory only, and gated against the agent
  itself by a confirmation the agent cannot give (the mechanism is chosen in clarify). Storage of
  the private key outside the repository (for example the macOS Keychain or a password manager's
  command-line tool, chosen in clarify), put there by the user in their own terminal or the tool's
  own interface, never through the agent's shell or a prefix that runs there, such as Claude
  Code's `!`. The leaked-key guidance in `docs/bootstrap.md` extended to the local copy. App
  permissions that make an approving review or a merge by the bot impossible, or a ruleset setup
  in which its approvals do not count, with a test. The toolkit's scripts and skills that write to
  GitHub use the bot token for the chosen writes, and the `AGENTS.md` rules say which writes go
  through it. An attribution line on every bot comment that carries a person's decision
  (`Decided by <login> in session, <date>:` followed by their words, with the login not
  @-mentioned so it does not notify on every comment). Setup guidance at the same point as 005's
  App setup, and a check that reports whether the bot identity is configured. Tests for the token
  handling, the gating and the attribution line.
- **Scope (out):** Git commit authorship (commits stay the person's, with the co-author line);
  the bot approving or merging pull requests; writes made by CI workflows, which already use
  `github-actions[bot]` or the board credential; platforms other than GitHub.
- **Depends on:** 005
- **Notes:** Raised in #92 after comparing with the Factory Kit, whose local scripts mint App
  tokens from a key path in `.env.github` and post as the App bot, so its state machine can tell
  the agent's comments from the person's; its pilot showed that a decision posted by the bot loses
  who made it unless the comment says so. Today the agent writes through the person's `gh` login,
  which can do everything the person can. Threat model: the coding agent runs as the same OS user
  as the key store, so whatever a minting script can read, the agent can read too, and it can print
  a token it asked for; "the agent never sees the key" holds only with a gate the agent cannot pass
  (a confirmation on every use, a separate helper process or OS user, or minting in CI). The key is
  in GitHub's secrets only today, so a local copy is one more place it can leak from; the claim of
  006 is a net gain over the person's full `gh` login, not "no new risk". Security is the deciding
  factor, as in 005: more setup steps are acceptable when they improve the user's security. The
  attribution line is a record, not proof: nothing (approvals, the dependency acknowledgement, the
  human-only labels in `AGENTS.md`) may treat a bot comment that says a person decided as that
  person's approval. Approvals risk: when the bot opens a pull request, the person who drove the
  work is no longer its author and could approve it as an independent reviewer; clarify must keep
  the constitution's non-author approval rule meaningful (for example the bot does not open pull
  requests, or the approval check counts the driving person as the author). If 005 chooses the
  `GITHUB_TOKEN`-only option, 006 brings its own App. Run `security-auditor` on 006's spec, since
  it adds a local credential store. Open questions for clarify: which writes move to the bot (all,
  or comments and board changes only); how key use is gated against the agent itself (a
  confirmation on every use such as Touch ID or a Keychain prompt, a separate helper, or minting in
  CI); how the key is stored and unlocked per session; whether the App is the same as 005's board
  App or a separate one with repository permissions only; whether an App's approving review can
  count toward a ruleset's required approvals; how a board owned by a personal account is handled
  if 005 keeps the Projects board (the App cannot reach it, so board updates stay with the person
  or move to CI).

### 007 — Board views: Epics by default, Phases as a table [status: planned]

- **Description:** Make the project board readable: bootstrap sets up an Epic board as the default
  view, Phase issues get titles that start with their roadmap ID, and a table of Phases grouped by
  their Epic is added (replacing or alongside the Phases kanban board, see Notes).
- **Outcome:** An adopter opens the board after bootstrap and sees one card per roadmap entry, with
  its progress, as the default view. Phase issues are told apart at a glance in the table, the
  issue list and PR titles, even when the title is truncated. A fresh board has no Phases kanban
  board, because bootstrap creates no views today; that board exists only where its owner made it.
- **Scope (in):** Phase 1 (titles): a roadmap-ID-first format (for example `007 · Phase 1: Kickoff — <Epic name>`)
  for the provisional Phase 1 issue (`provisional_phase_title` in `scripts/roadmap_issues.py`) and
  for the Phase issues that `sync-task-issues.py` creates from `tasks.md`; a spec directory without
  a three-digit roadmap prefix keeps the `Phase N: …` title (`roadmap_id_for_path` returns `None`).
  Code tied to the current format is updated too: `pr_conventions.py` (it reads `phase-<number>`
  from the branch name and matches `Phase <number>` plus a colon in the issue title) and the
  `startswith("Phase 1: Kickoff")` test in `scripts/sync-task-issues.py` that decides whether a
  closed provisional Phase 1 may still be retitled, preferably changed to match on the marker.
  Documentation and tests that quote the title (`AGENTS.md`, `docs/spec-workflow.md`,
  `scripts/README.md`, `scripts/test_sync_task_issues.py`, `scripts/test_sync_roadmap_issues.py`)
  are updated with it, and a decision is made on whether existing Phase issues are retitled. Phase 2
  (board views): the Epic board as the default view and a Phases table filtered to Phase issues,
  grouped by parent Epic and showing Status and linked pull request (the Phase number comes from the
  title, with no new board field), created or checked by `bootstrap.py github` where the GitHub API
  allows it, otherwise written as a manual step in `docs/bootstrap.md` with `--check` reporting its
  absence; the `bootstrap-guide` skill and the docs updated to match.
- **Scope (out):** a new board layout for work that is not a roadmap Epic or Phase; a new board
  field for the Phase number; changing the Status options or the sync-project-status rules;
  platforms other than GitHub.
- **Depends on:** none
- **Notes:** Raised from the Phases board of this repository, where Phase 1 cards of different
  Epics look alike and the same roadmap item shows up as an Epic, a SPEC issue and a Phase.
  Bootstrap creates no project views today (`bootstrap_github.py` handles the Status options,
  `Roadmap order`, the repository link and a check of the board workflows). Both syncs already
  retitle existing issues when the generated title differs, through the same `update_issue_content`
  (the roadmap sync only for the provisional Phase 1, while `tasks.md` is missing), so an Apply run would retitle every
  open Phase once the title functions change; keeping old titles needs new guard logic. Open
  questions for clarify: whether the GitHub API can create and configure project views, or can only
  read them (which would still allow a `--check`), with `docs/bootstrap.md` already printing the
  board workflows as a manual step; the exact title format, including whether to keep the Epic name suffix (the branch pattern allows a prefix and
  the title check `\bPhase\s+N\s*:` already matches `007 · Phase 1: Kickoff`, so clarify can confirm
  this quickly); whether the Phases table replaces the Phases kanban board or the two can both
  exist; how existing adopters' boards migrate (retitle open Phases only, or retitle none). The
  Phase order matters: titles come first because they change what the views show. Phase 2 edits the
  `bootstrap-guide` skill and the board setup that entries 001, 004 and 005 also touch, so
  sequence the pull requests to avoid conflicts; there is no hard prerequisite.

### 009 — Optional code-owner review in bootstrap [status: deferred]

- **Description:** An optional step in the guided bootstrap that makes changes to `.github/` and
  `scripts/` need a code owner's approval, through a `.github/CODEOWNERS` file and the "Require
  review from Code Owners" setting in the default branch ruleset.
- **Outcome:** An adopter can choose, during bootstrap, to protect the workflows and scripts that
  run with write tokens and secrets, with a plain explanation of what the option does. A solo
  project is not offered it.
- **Scope (in):** `init` and `start`, and the `bootstrap-guide` skill with the `check --json`
  status, ask whether to enable code-owner review and explain what it is and what it protects
  against; the answer is stored as a new optional `[review]` key in `project-context.toml`, where
  a missing key means "not enabled" so existing files stay valid (`scripts/project_context.py`,
  `project-context.example.toml` and its section in `scripts/README.md` change with it); the
  question is skipped when `[review] required_approvals` is 0 (solo project); when enabled, the
  person running the bootstrap is the default code owner of `.github/` and `scripts/`;
  `.github/CODEOWNERS` is written into the working tree and added to the files the bootstrap pull
  request commits (`BOOTSTRAP_FILES` in `scripts/bootstrap_steps.py`, which today lists other
  changed files and never adds them); `bootstrap.py github` previews, applies and checks the
  ruleset setting only when the answer is yes, and answering "no" leaves the setting unmanaged, so
  a hand-set value is neither changed nor reported as drift; the rules table in
  `docs/ci-and-conventions.md`, the "Code owners" bullet and the machine-readable status table in
  `docs/bootstrap.md` are updated; tests for the question, the skip, the missing key, the file and
  the ruleset change.
- **Scope (out):** enabling it in this repository (decided in #115 to leave as is); code owners for
  paths other than `.github/` and `scripts/`; changing how `required_approvals` or the
  constitution set the approval count.
- **Depends on:** none
- **Notes:** Raised in #115 (closed as not planned, deferred to this entry). With a single code
  owner, that person's own pull requests touching those paths cannot satisfy code-owner review,
  because GitHub does not let an author approve their own pull request; this is a known limitation

### 011 — Board auto-add workflow in bootstrap [status: planned]

- **Description:** Make the bootstrap engine and the `bootstrap-guide` skill report and ask for the
  board's "Auto-add to project" workflow, so typed issues (`SPEC:`, `CI:`, `DOCS:`, `FIX:`,

  whether the workflow is on, as it does for "Pull request linked to issue" and "Auto-add

  repository or filter, so enabling it and choosing the filter stay manual steps.
- **Outcome:** After `bootstrap.py github` and `check`, an adopter whose "Auto-add to project"

  then land on the board on their own; existing issues are not added all at once; each is
  added only when it is next updated.
- **Scope (in):** The workflow's on or off state, and when it is off the manual step with the
  repository and filter, in `bootstrap.py github` output and in `check --json`; the

  tests for the new step in the engine, the `check --json` format and the guide. Clarify decides
  whether it extends the existing board-workflow step or becomes a new step, and which status wins
